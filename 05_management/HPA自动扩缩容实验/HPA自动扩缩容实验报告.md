## 1. 实验目标与结论摘要

**目标**：为 user-service 配置资源 requests/limits 与 CPU 利用率型 HPA，用压力测试抬升负载，验证「压力升高 → Pod 扩容、压力消失 → Pod 缩容」，并记录吞吐量、平均/P95 响应时间与错误率；重复 3 轮验证可复现性。

**结论**（3 轮全部复现，无一例外）：

| 验证项 | 结果 |
|---|---|
| 压力升高后 Pod 增加 | ✅ 三轮均按 `2 → 4 → 6 → 8` 扩容（每 60s +2，与策略一致），峰值顶到 maxReplicas=8 |
| 压力消失后 Pod 减少 | ✅ 三轮均在约 300s 稳定期后开始缩容，每 120s −1（`8→7→6→5→4→3→2`），约 15~16 分钟完全回落到 minReplicas=2 |
| 扩容对性能的改善 | ✅ 平均延迟 2.3~3.1s（2 副本期）→ 1.07~1.15s（6-8 副本期），P95 从 5.8~6.2s 降到 2.3~2.6s；吞吐从 4.0 升至 11.4 RPS |
| 错误率 | ✅ 三轮共 5,620 个请求全部 HTTP 200，**错误率 0.00%**，无超时、无 5xx、无 Pod 重启（实验期间） |

## 2. 实验环境

### 2.1 集群与服务

- 集群：Docker Desktop 内置 Kubernetes v1.36.1，单节点 `docker-desktop`，命名空间 `online-teach-micro`；metrics-server 正常（HPA 指标 15s 粒度）。
- 被测服务：`user-service`（Deployment 2 副本起步，每副本 Gunicorn 2 worker，容器端口 8000）。
- 流量路径（与生产一致，未为实验改动任何集群配置）：

  ```
  宿主机压测脚本 → frontend NodePort(:30081) → gateway(backend:8000)
      → user-service ClusterIP(:8000) → kube-proxy 负载均衡到全部就绪 Pod
  ```

- 节点资源充足（空闲 CPU >90%、内存 ~50%），保证瓶颈在被测服务的 CPU limit 而非节点容量。

### 2.2 资源配额与 HPA 配置（实验中使用仓库现有配置）

Deployment（`k8s/micro/user-service.yaml`）：

| 项 | 值 |
|---|---|
| CPU request / limit | 100m / 500m |
| 内存 request / limit | 128Mi / 256Mi |
| 存活/就绪探针 | `/api/live/`、`/api/ready/`（10~15s 周期，failureThreshold=3） |

HPA（`k8s/micro/user-service-hpa.yaml`，autoscaling/v2）：

| 项 | 值 | 含义 |
|---|---|---|
| minReplicas / maxReplicas | 2 / 8 | 副本上下限 |
| 指标 | CPU Utilization 70% | 按 **request** 的百分比（100m 的 70% 即 70m） |
| 扩容策略 | 30s 稳定窗，+2 Pod / 60s | 防抖动、防扩容过猛 |
| 缩容策略 | 300s 稳定窗，−1 Pod / 120s | 防频繁缩容（缩容保守是刻意设计） |

### 2.3 压测端点选择

压测 `POST /api/auth/token/`（登录，账号 `demo_teacher`）。Django 默认 PBKDF2-SHA256 密码校验为 **CPU 密集**操作（单次登录约 0.3~0.5 核·秒），能在少量并发下把 Pod CPU 打到 limit，是驱动 CPU 型 HPA 的理想负载；同时登录是只读路径（不改业务数据），重复数千次无副作用。

## 3. 实验方法

### 3.1 脚本

| 脚本 | 作用 |
|---|---|
| `hpa_loadtest.py` | 固定并发线程压登录接口，逐请求记录时间戳/延迟/状态码 → `load_requests.csv` + `load_summary.json` |
| `hpa_metrics_sampler.py` | 每 15s 采集 HPA 当前/期望副本、CPU 利用率%、Pod 数、`kubectl top` 实测 CPU(m)/内存(Mi) → `metrics_timeline.csv` |
| `hpa_experiment.sh` | 单轮编排：前置检查 → 启动采样 → 基线 60s → 高压 240s → 冷却 780s → 取证（`kubectl describe hpa`、events、最终状态） |

本报告中的分桶统计与跨轮对比，均由上述两类原始 CSV（`load_requests.csv` × `metrics_timeline.csv`）按时间戳联算得出，可直接复算。

### 3.2 单轮时序（三轮完全一致）

```
t=0        基线观察 60s（2 副本，CPU 1~3%）
t=60~300   高压：12 并发线程持续压登录接口 240s
t=300~     冷却：负载归零；采样 780s + 轮询直到副本回到 2
```

每轮开始前都确认 HPA 已回到 minReplicas=2 且低负载（轮与轮之间等待自然缩容完成，未人工干预副本数）。

### 3.3 指标定义

- 吞吐量 = 总请求数 ÷ 压测时长（RPS）；延迟统计基于成功（HTTP 200）请求；
- 错误率 = 非 200（含超时/连接错误）÷ 总数；压测客户端单请求超时 30s（实际最大单请求延迟 6.5s，未触发）。

## 6. 分析

1. **HPA 行为与配置逐条吻合**：扩容每 60s 最多 +2、缩容 300s 稳定期后每 120s −1、峰值被 maxReplicas=8 封顶、低谷被 minReplicas=2 托底——所有决策事件（`SuccessfulRescale`）都带原因（超目标扩容 / 全指标低于目标缩容），三轮无一例外的复现说明该配置行为确定性强。
2. **扩容显著改善过载表现，但有几分钟「空窗」**：从负载上升到容量到位约需 3~4 分钟（指标滞后 + 稳定窗 + 逐级 +2 的爬坡策略），期间平均延迟高达 2.3~3.1s。这是「防抖动」策略的代价：换取的是三轮零抖动、零误扩。若业务对突发更敏感，可缩短扩容稳定窗或放大单批扩容步长。
3. **request=100m 偏小，利用率读数被放大**：Pod 实际用 450m 时利用率为 450%（450m/100m），一次即触发大幅扩容并很快顶到 maxReplicas。对本服务（登录 CPU 密集）结果反而是好的（扩容果断），但建议 request 调到 200~250m 让「70% 目标」语义更贴近真实占用，避免小幅负载就冲满 8 副本。
4. **过载表现是延迟而非错误**：CPU 被 limit 限流时，Gunicorn 同步 worker 让请求排队，三轮 5,620 个请求 0 失败。但注意 P99 逼近 6s——对登录类接口已不可接受，生产上应在网关/客户端层设置更严的超时与降级。
5. **探针在饱和边缘出现超时告警但未误杀**：高压期观察到若干 `Readiness probe failed: context deadline exceeded`（worker 被 PBKDF2 占满，探针请求排队 5s 超时），均未连续 3 次失败，未触发摘除/重启；轮 2、3 零重启。建议：CPU limit 逼近时探针余量不足，可适当调大探针 timeout 或为探针预留专用 worker/端口。
6. **缩容保守性符合设计取舍**：回到 2 副本全程需 ~16 分钟（300s 稳定期 + 6 步 × 120s）。对登录这种间歇性高峰的业务，这个节奏能避免「缩了又扩」的震荡，本轮实验中未出现任何扩缩容抖动（throttling）现象。

## 7. 复现方式

```bash
# 前提：集群就绪、HPA 已部署、副本回到 2
kubectl get hpa -n online-teach-micro          # 确认 REPLICAS 2 / 低负载
bash scripts/hpa_experiment.sh roundN 12 240 780   # 单轮：基线60s+压测240s+冷却780s
# 跑完后产物在 raw/roundN/，与本次提交的 round1~3 结构一致
```

脚本环境适应性说明（`hpa_experiment.sh` 已内置处理）：

- **Python 解释器**：依次自动尝试 `python` → `py -3` → `python3`；也可用 `HPA_PYTHON=<路径>` 显式指定。从 cmd 启动 Git Bash 时 PATH 常缺少 `python`，此时会自动落到 Windows 启动器 `py -3`。
- **防覆盖**：目标轮次目录已有 `load_summary.json` 时拒绝重跑，保护已完成实验的原始数据；确需覆盖用 `FORCE=1 bash scripts/hpa_experiment.sh round1 ...`。
- **Git Bash 限制**：本机 `/usr/bin/sleep`、`/usr/bin/grep` 不可执行，脚本内分别用 Python 等待与 Python 过滤替代。
