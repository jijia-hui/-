## 一、主讲稿（约 3 分钟，可直接背诵）

> **开场一句话**：
> 我讲一个我们真实发生的案例：8 月 31 日微服务 CD 流水线首次上线当晚，第一次运行就失败了，**失败是流水线自己发现的，不是人盯出来的**——从失败到修复复绿一共 10 分钟。

### 第 1 步：怎么发现的（部署即验证，失败自动留证）

> 我们的 CD-Micro 流水线是"部署即验证"：部署完必须通过 rollout 状态、健康检查、版本号核对，再跑全量 E2E 回归（UC01~UC14，58 项断言），**任一步失败整条流水线立即变红、后续步骤不再执行**。
>
> 当晚 18:26，提交 5358642（后端拆分三个微服务 + 流水线配套，116 个文件）触发 CD-Micro 首跑，运行 ID **33382400841**。前几步"变更检测 → 测试 → 构建推送镜像 → 部署并健康检查"**全部绿灯**，最后一步 E2E 回归**整步变红**：E2E 脚本的第一件事是前置探活（连 `http://127.0.0.1:8080` 的四个 `/api/health/`），4 项**全部 FAIL**，紧接着一个未捕获的 `requests.exceptions.ConnectionError` 异常栈直接打出来，最后一行就是 **`[Errno 111] Connection refused`**（Linux 的"连接被拒绝"），脚本当场中止——还没跑到 58 项断言就 fail-fast 暴露了问题（这条日志具体在哪看，见下方 §二·D）。
>
> 同时，流水线里有一个 `if: failure()` 自动触发的**失败诊断步骤**，当场把 Pod 状态、`kubectl describe`、四个服务各 100 行日志全部归档成构建产物——不需要人事后登机器翻，证据自动留在 Actions 的 artifact 里。

### 第 2 步：怎么定位的（三步：绿红定界 → 读首错 → 对证据）

> 我的方法是**先看哪些步骤绿、哪个步骤红，界定问题域，再读红步骤的第一条错误**：
>
> 1. **绿红定界**：部署步骤是绿的，说明 rollout 全过、`/api/health/` 全 200、版本号核对一致——**集群和应用本身是健康的**；红的是下一步 E2E，报的是 `Connection refused` 连本机 8080。问题域立刻收窄：不是应用代码，不是镜像，不是 K8s，而是**"流水线步骤之间的访问通道"**。
> 2. **读首错**：E2E 第一条错误就是 `Connection refused 127.0.0.1:8080`——E2E 是从 runner 本机经 port-forward 访问集群的，这个地址拒连说明通道不存在。
> 3. **对证据**：去读部署脚本 `scripts/deploy_micro_k8s.sh`，看到第 66-70 行——部署脚本为了做健康检查，自己起了两个后台 `kubectl port-forward`，然后 `trap 'kill ...' EXIT`：**脚本一退出就把自己的 port-forward 杀掉了**。而 GitHub Actions 的每个 step 是独立进程，部署步骤结束、E2E 在下一个 step 才启动——那一刻通道已经被销毁了。

### 第 3 步：根因与修复

> **根因一句话**：不是应用问题，是**流水线编排问题**——port-forward 的生命周期绑定在"部署步骤"内，而 E2E 在"下一个步骤"，资源生命周期不覆盖使用方。
>
> **修复**（提交 **b80d2a7**）：在部署与 E2E 之间新增一个独立步骤"建立本机访问通道"——用 `nohup` 起作业级后台 port-forward（存活到整个 job 结束），并用 curl 轮询 30 次×2 秒确认通道就绪才放行下一步。改动只加步骤、不动应用代码。

### 第 4 步：验证闭环

> 18:36 复跑，CD-Micro 第二次运行 **33383200990 全绿，流水线内 E2E 58/58**；之后组员提交的 HPA、故障演练等 4 次推送全部自动触发、自动通过（运行 33462976899 / 33468539525 / 33468646291 / 33469238973）——证明修复稳定，也顺带证明"提交后自动构建部署"持续在工作。

### 收尾（方法论，答出高度）

> 这个案例给我们的方法论是三条：
> 1. **部署即验证**：部署不等于发布成功，健康检查 + E2E 过了才算——所以失败能在 4 分钟内被流水线自动暴露；
> 2. **绿红定界再读首错**：先确定问题在哪个域（应用/镜像/集群/编排），再看第一条错误，不瞎猜；
> 3. **失败自动留证**：`if: failure()` 的诊断步骤把 Pod 状态、describe、服务日志自动归档，事后可查、答辩可证。
>
> 这也正好呼应任务书要求的四项可观测能力——日志、健康检查、就绪检查、版本号——我们排查全程用的就是这些入口。

### D. "Connection refused 127.0.0.1:8080" 这条错误具体在哪里看（评委最可能追问）

**① 在线第一现场：红 run 的 E2E 步骤日志**

仓库 → **Actions** → 左侧 **CD-Micro** → 红色 ❌ 的 **CD-Micro #1**（run **33382400841**，2026-08-31 18:26，提交 5358642）→ 点进 job「部署微服务到 Kubernetes 并做 E2E 回归（kind）」→ 展开红色步骤「端到端回归（E2E-TC01~14 + 级联清理，经网关）」，日志开头就是：

```
==== 微服务版端到端回归（E2E-TC01~14 + 级联清理） 2026-08-31 18:xx:xx ====
FAIL  [setup] 网关 /api/health/: HTTPConnectionPool(host='127.0.0.1', port=8080): Max retries exceeded with url: /api/health/ (Caused by NewConnectionError(...
FAIL  [setup] user-service 探活: HTTPConnectionPool(host='127.0.0.1', port=8080): ...
FAIL  [setup] course-service 探活: ...
FAIL  [setup] assignment-service 探活: ...
Traceback (most recent call last):
  File ".../04_tests/e2e/run_e2e_micro.py", line 140, in gateway_alive
    code_resp = requests.get(BASE + '/internal/users/?ids=1', timeout=10)
  ...
requests.exceptions.ConnectionError: HTTPConnectionPool(host='127.0.0.1', port=8080): Max retries exceeded with url: /internal/users/?ids=1 (Caused by NewConnectionError(...: Failed to establish a new connection: [Errno 111] Connection refused'))
```

- `Errno 111` 是 Linux 的"连接被拒绝"——**runner 本机的 8080 端口没有任何进程在监听**，也就是 port-forward 已死；
- `host='127.0.0.1', port=8080` 证明 E2E 是从 runner 本机经 port-forward 访问集群的，不是集群内服务地址——问题域因此锁定在"本机通道"而非"集群/应用"。

**② 构建产物 artifact（自动归档的日志文件）**

同一 run 页面底部下载 **`micro-deploy-artifacts`** → 里面的 `e2e_micro.log`（流水线 `| tee e2e_micro.log` 落盘）保存着同样的 FAIL 探活行；`deploy_micro_k8s.log` 则证明部署步骤当时是全绿的（rollout、健康检查、版本号核对全过）——两份文件一对比，"绿的部署 + 红的 E2E"一目了然。

**③ 离线备份（现场断网/打不开 GitHub 时）**

- `git show b80d2a7`——修复提交信息原文就写着："**部署脚本退出时会清理自己的 port-forward，导致后续 E2E 步骤连接 127.0.0.1:8080 被拒**"；
- `05_management/流水线记录/image-1.png`——当日 8 次运行列表截图（CD-Micro #1 红 ❌、#2 绿 ✅）；
- `05_management/流水线记录/20260831_流水线记录报告.md` 运行表第 4 行"❌ E2E 步骤失败"。

**④ 这段日志为什么长这样（对应代码，能讲出出处最加分）**

`04_tests/e2e/run_e2e_micro.py` 的 `gateway_alive()`（115-145 行）：四个探活 GET 包在 `try/except` 里，失败时打印 `FAIL [setup] ...`（异常消息截断 120 字符，所以 FAIL 行本身可能截不到 "Connection refused" 字样）；随后的内部接口检查（第 140 行）**没有**包 try，`ConnectionError` 直接抛出终止脚本——完整的 `[Errno 111] Connection refused` 就在这最后一行异常栈里。也就是说真实日志是"**前置探活 4 项 FAIL + 1 个未捕获异常即中止**"，不是"58 项逐条失败"——答辩时这样表述更准确，而且 fail-fast 暴露得更早，是加分点不是弱点。

### E. "E2E 从 runner 本机经 port-forward 访问集群"——链路解释（画给评委看）

**先说场景**：CD 流水线的部署目标是 kind 集群——它不是远程服务器，而是**跑在 GitHub Actions runner 这台临时虚拟机上的几个 Docker 容器**组成的 Kubernetes。而 E2E 脚本（`run_e2e_micro.py`）是一个**普通 Python 进程，跑在 runner 上、集群外面**，它请求的是 `E2E_BASE_URL=http://127.0.0.1:8080`——一个 runner 本机的回环地址。集群里的 Service IP（如 10.96.x.x）它默认根本够不着，必须有人在本机 8080 上"代收"并把流量转进集群。

**port-forward 就是这条临时隧道**：`kubectl port-forward svc/frontend 8080:80` 会在**执行 kubectl 的机器**（runner）的 127.0.0.1:8080 起一个监听进程，把收到的 TCP 连接经 K8s API Server 的隧道转发到集群内 `svc/frontend` 的 80 端口。关键性质：**隧道由 kubectl 进程撑着——进程活隧道在，进程死，8080 上就没有任何监听者**。

一次请求的完整链路（答辩时在白板/纸上画这条链）：

```
run_e2e_micro.py（runner 上的 Python 进程）
  │ requests.get('http://127.0.0.1:8080/api/health/')
  ▼
runner 本机 127.0.0.1:8080  ← 监听者是 kubectl port-forward 进程（临时隧道）
  │ 经 K8s API Server 隧道进集群
  ▼
online-teach-micro 命名空间 svc/frontend :80 → frontend Pod（nginx）
  │ nginx 把 /api/* 反代给后端入口
  ▼
svc/backend :8000 → gateway Pod → 按 /api/users|courses|assignments 前缀路由
  ▼
user / course / assignment 三个业务服务 Pod（MySQL 三库）
```

**为什么这么设计**（评委追问"为什么不直接访问服务"时）：

1. kind 是 CI 里的临时本地集群：节点本身是 runner 内的 Docker 容器，Service 地址没有映射到宿主机端口，从 runner 的 127.0.0.1 无法直达；port-forward 是 CI 中最简单、确定性的访问方式；
2. E2E 脚本**环境无关**：同一个 BASE_URL `http://127.0.0.1:8080`，在 test4 的 docker compose 环境 8080 是 compose 映射的端口，在流水线里 8080 是 port-forward——脚本一行不改两处通用；
3. E2E 本来就站在集群外操纵集群：验证码注入靠 `E2E_EXEC_PREFIX="kubectl ... exec deploy/user-service --"`，访问与注入都从 runner 发起，逻辑一致。

**这句话如何衔接故障**：隧道的寿命 = 拉起它的 kubectl 进程的寿命，而 GitHub Actions **每个 step 是独立进程**。部署 step 的脚本起了 port-forward，又在 `trap 'kill ...' EXIT`（`deploy_micro_k8s.sh:70`）里随脚本退出杀掉了它；E2E 在**下一个 step** 才发起请求，此刻 8080 已无监听进程——**runner 本机内核**直接拒绝连接（RST），Python 报 `[Errno 111] Connection refused`。注意：请求根本没出 runner 本机，所以集群内服务再健康也无济于事——这正是"部署步骤全绿、E2E 步骤全红"能同时成立的原因。修复（b80d2a7）就是把 port-forward 提为独立 step、用 `nohup ... &` 起在 **job 级**：step 结束不杀进程，隧道活到整个 job 结束，后续 E2E 随时可用。

## 三、备用案例（评委追问"还有吗/换个例子"时用，各 1 分钟）

**案例 C（应用级，最好懂）：容器启动即 unhealthy 循环重启**
- 现象：首次 `docker compose up`，三个业务服务全部 unhealthy、反复重启。
- 查法：一条 `docker logs otp-micro-user`，直接看到 Python 栈 `Error loading MySQLdb module. Did you install mysqlclient?`——新建的三个服务漏了单体工程里有的 `pymysql.install_as_MySQLdb()` 兼容垫片。
- 修复：三个服务 `config/__init__.py` 补一行垫片，重建镜像恢复。**1 分钟定位，日志可查是关键**。

**案例 B（供应链级，最能体现深度）：GHCR `frontend:latest` 被实验版本覆盖**
- 现象：健康检查返回张冠李戴的响应——`/api/health/` 返回的竟是 assignment-service 的 health，`/api/health/user/` 返回 Django 404，网关访问日志里**根本没有这些请求**。
- 查法（三分排除）：① 同路径直连网关 8000 端口 → 200，排除网关/服务；② 响应头含 Django corsheaders 的 `Vary: origin`，说明请求到了某个业务服务而非网关；③ 进前端容器 `cat nginx.conf` → 发现是"前端直连三微服务"的实验配置，镜像创建时间是当天上午——**GHCR 的 frontend:latest 被组员的实验构建覆盖了**。
- 修复与教训：改用已验证镜像复绿；**部署必须固定版本标签（SHA），实验镜像禁止推 latest**——这正是任务书"镜像要有版本号，不能只依赖 latest"的现实印证。CI 已同时推送 SHA 标签可供固定。

| 可能的追问 | 30 秒回答 |
|---|---|
| "Connection refused" 具体在哪里看到的？ | 红 run 33382400841 的 E2E 步骤日志：4 行 `FAIL [setup] 探活: HTTPConnectionPool(host='127.0.0.1', port=8080)...` + 最后一行异常栈 `[Errno 111] Connection refused`；同一 run 的 artifact `e2e_micro.log` 也归档了。Errno 111 = runner 本机 8080 无进程监听 = port-forward 已死。 |
| E2E 为什么要从 runner 本机经 port-forward 访问集群？ | kind 集群本身跑在 runner 的 Docker 里，Service 地址没映射到宿主机，runner 上的 E2E 脚本（普通 Python 进程）够不着；`kubectl port-forward` 在 runner 的 127.0.0.1:8080 起一条经 API Server 进集群的临时隧道。隧道随 kubectl 进程存亡——这就是"步骤间生命周期"问题的来源（详见 §二·E 链路图）。 |
| 部署步骤是绿的，能说明部署成功吗？ | 能说明**集群内**成功：rollout status、`/api/health/` 200、版本号核对都在部署步骤内、经它自己活着的 port-forward 验证过。红的是步骤间通道，属于流水线编排问题，不是应用问题。 |
| 为什么 E2E 不放在部署同一个步骤里？ | 分步是为了职责清晰 + 失败定位粒度（哪步红一眼看出）。我们选择修通道生命周期（作业级 nohup port-forward + 就绪轮询），而不是把步骤合并。 |
| 如果当时不是 port-forward 问题，你还会查什么？ | 按层次排除：`kubectl get pods`（Pod 是否 Ready）→ `describe`（探针失败/镜像拉取失败事件）→ `logs`（应用栈）→ 网关路由。案例 C 就是这么用 logs 直接看到 Python 栈的。 |
| 健康检查和就绪检查有什么区别？ | `/api/live/` 存活探针不查 DB，DB 抖动不会误杀重启；`/api/ready/` 就绪探针查 DB 连通性，DB 不可用时摘除流量但不重启。两者 + `/api/health/`（含版本号）对应 K8s livenessProbe/readinessProbe。 |
| 版本号怎么和部署对上？ | 探针响应的 `version` 字段 = `APP_VERSION` 环境变量 = 镜像标签；CI 注入提交 SHA / `v*` 标签名，现场可与 GHCR 和 Actions 运行记录对账。 |
| 怎么保证不再发生？ | 通道改为独立步骤、作业级生命周期；`if: failure()` 自动归档诊断；修复后 5 次连续运行全绿（含组员提交自动触发）。 |
