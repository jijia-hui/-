## 1. 项目概述

本项目以上学期的小组项目「在线教学与实训平台」(Django 单体架构)为改造对象,在两周小学期内完成**从单体到微服务的完整改造与云原生交付**。平台业务为:学生注册选课、查看作业、在线提交代码;教师创建课程/作业、查看提交并评分;管理员后台管理。

**改造目标**(依据《软件工程基础实践》任务书):

1. 在原系统基础上拆分出**至少 3 个业务微服务**(网关、前端、数据库不计入);
2. 每个服务能**单独构建、测试、部署**;
3. 代码提交后,**相关微服务自动完成构建、测试、制作镜像和部署**;
4. 所有后端公开接口都有 API 测试,全部业务场景(UC01~UC14)端到端回归;
5. 具备服务日志、健康检查、就绪检查、版本号与部署失败排查能力。

**最终成果一览**:

| 成果 | 数据 |
|---|---|
| 业务微服务 | 3 个(user / course / assignment)+ 1 个 Nginx API 网关 |
| 数据库拆分 | 同一 MySQL 实例三库隔离(otp_user / otp_course / otp_assignment),7 张业务表单一归属 |
| 对外 API 兼容性 | 路径/请求/响应/状态码逐条与单体版一致,前端与 E2E 脚本零修改 |
| 测试 | 单体版 179 项 + 微服务版 154 项全部通过;服务级 API 测试 98 项全绿;E2E 两轮实测 58/58 |
| CI/CD | 单体 + 微服务共 4 条流水线;CD-Micro 6 次真实运行记录(含组员提交自动触发) |
| 部署形态 | Docker Compose(源码构建 / GHCR 拉取两种)+ Kubernetes(kind,双命名空间隔离) |
| 云原生增强 | HPA 自动扩缩容、F1~F6 故障演练流水线、版本化镜像、三类探针 + 版本号对账 |

## 2. 原系统概况与改造基线

原系统为典型三层单体:Django 6 + DRF 提供 REST API,React 18 + Vite + Ant Design 前端,MySQL 8 存储,`apps/` 单应用内含 users / courses / enrollments / assignments / submissions / email_verification_codes 全部模型,数据库外键级联维护一致性。

改造前先做了两件事:

1. **打标签固定基线**:8/25 打 `monolith-start` 标签,单体源码完整保留在 `web_backend/`,作为改造参照与性能对比基线;
2. **补测试护栏**:在动架构之前先把三层自动化测试补齐(单元 39 + 集成 93 + E2E 共 179 项,8/26 全绿)。

## 3. 微服务划分方案

### 3.1 划分结果

| 服务 | 职责 | 数据库 |
|---|---|---|
| user-service | 注册(邮箱验证码)、登录签发 JWT、用户查询、删除用户(跨服务级联清理)、Django 管理后台 | otp_user |
| course-service | 课程 CRUD、选课/退课、选课关系与课程归属查询 | otp_course |
| assignment-service | 作业 CRUD(含参考文档)、学生提交、教师评分、提交记录查询 | otp_assignment |
| gateway(Nginx,不计业务服务) | 按 `/api` 路径前缀路由到三服务;屏蔽 `/internal/*` 内部接口 | — |

### 3.2 划分原则(为什么是这 3 个)

1. **按业务能力划分,不按用例/页面机械拆分**。三个服务对应"人"、"课"、"课业产物"三个业务概念,边界稳定。
2. **数据 ownership 单一**:每张表只归一个服务,服务间只存对方主键 ID,不跨库联表。
3. **不拆"评分"服务**:score 与提交同表同事务,拆开会把每次评分变成跨服务事务。
4. **不拆"认证"服务**:JWT(HS256 共享密钥)本地验签,鉴权零跨服务调用,Token 不落库。
5. **不为架构而架构**:没有缓存与异步消息的真实需求,不引入 Redis / RabbitMQ
6. **作业与提交同服务**:前端作业页一次拉取"作业 + 提交列表"是最高频读写关联,拆开会变成两次跨服务聚合。
7. **网关用 Nginx**:路由是纯路径前缀映射,零代码维护;编排内网关服务名沿用 `backend:8000`,**前端镜像无需任何改动**。

### 3.3 跨服务调用与失败策略

5 条调用链路,按业务后果分两类处理(详见《跨服务调用说明.md》):

| 链路 | 场景 | 策略 |
|---|---|---|
| course → user | 课程展示补全教师/学生用户名 | **降级**:用户名返回 null,接口不失败 |
| assignment → user | 提交列表补全学生用户名 | **降级**:student_name 返回 null |
| assignment → course | 作业归属校验、提交选课校验、评分授课校验 | **快速失败**:503,写操作绝不绕过校验(fail-closed) |
| course → assignment | 删除课程级联删除作业与提交 | **快速失败**:502,课程不删除 |
| user → course / assignment | 删除用户级联清理 | **快速失败**:502,用户不删除 |

设计准则:**展示类数据可降级(可用性优先),校验/一致性数据必须快速失败(正确性优先)**。原数据库外键级联删除改为跨服务编排,以"下游失败则上游不删"保证最终一致。

### 3.4 对外行为保持不变

对外 REST API 与单体版逐条一致(路径、请求/响应、状态码),前端与既有 E2E 脚本零修改即工作。仅两处内部实现差异:登录 Token 由 DRF 数据库 Token 换为无状态 JWT(头格式与有效期 24h 不变);级联删除由数据库外键改为服务编排(行为一致)。

## 4. DevOps 与云原生实践

### 4.1 容器化与编排

- 全组件容器化:前端、三个业务服务、网关各有独立 Dockerfile;四套 Compose 编排覆盖「单体/微服务 × 源码构建/GHCR 拉取」;
- **免克隆部署**:`docker-compose.micro.prod.yml` 单文件自包含(MySQL 三库初始化 SQL 以 compose configs 内联),空目录实测一条命令拉起 6 容器全 healthy;
- 微服务版容器名 `otp-micro-*`、独立卷与命名空间,与单体版可同时运行,便于对比。

### 4.2 CI/CD 流水线(GitHub Actions)

单体(ci/cd)与微服务(ci-micro/cd-micro)共 4 条流水线。CD-Micro 关键设计:

- **按路径检测变更,只重做发生变更的服务**(git diff 按目录判定),版本号 = 提交 SHA / `v*` 标签,另推 latest;
- 流水线顺序:变更检测 → 变更服务测试(SQLite,无需数据库,失败即止)→ 构建/推送 GHCR → kind 部署(rollout + 健康检查 + 版本号核对 + /internal 屏蔽校验)→ **全量 E2E 回归(UC01~UC14,58 项断言)** → 产物归档(部署日志 / E2E 报告 / 失败诊断:Pod 状态 + describe + 各服务日志);
- 任一环节失败即停止,后续部署不执行。

验收时 CD-Micro 已有 6 次真实运行记录(1 次失败已修复复绿,含组员提交 HPA / 故障演练自动触发并通过)。

### 4.3 Kubernetes 部署

- 单体 `online-teach`、微服务 `online-teach-micro` 双命名空间隔离;每服务独立 Deployment / Service;
- 三类探针:`/api/live/`(存活,不查 DB,防误杀)、`/api/ready/`(就绪,含 DB 检查)、`/api/health/`(合并探活 + **版本号**,版本号 = 镜像标签,可现场与 GHCR/流水线对账);网关另暴露 `/api/health/{user,course,assignment}/` 逐服务探活;
- **HPA**:user-service 2~8 副本,CPU 70% 触发,扩容 30s 稳定窗 + 缩容 5 分钟稳定窗,防抖动;
- **故障演练**:`fault-drill.yaml`(F1~F6 六种故障,支持 workflow_dispatch 手动触发 + 自动修复)与 `scripts/fault-inject.sh` 配套,演练含 Pod 删除、镜像回滚(rollout undo)等场景。

## 8. 结语

本次改造的收获不在"拆出了几个服务",而在三点:

1. **先测试后重构**:179 项回归护栏让拆分全程"对外行为不变"可被机器验证,而不是靠人肉比对;
2. **按业务能力而非技术分层划界**,配合"数据 ownership 单一"原则,拆分后没有出现一处罚级的跨库联表或分布式事务;
3. **失败策略是微服务的核心设计**:同一套内部调用,"展示可降级、校验必快速失败"的显式约定,比调用本身更值得写进文档与测试。
